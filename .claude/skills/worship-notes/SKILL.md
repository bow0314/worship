# Worship Notes（主日敬拜筆記）

把當週的敬拜歌詞／流程 PDF 轉成這個 repo 既有的兩份 HTML 筆記,或是為既有筆記補上連結(YouTube／樂譜／歌詞PDF)。這兩份檔案共用一套固定的視覺設計系統,新筆記的正確做法**不是從零手刻 HTML**,而是複製最新的一份範本檔案、只替換內容。

在動手改結構之前,先讀 `references/template-structure.md`——裡面說明兩份檔案的差異、`.song` 區塊的固定寫法、階段色 `s1`~`s4` 的規則,以及最容易漏掉的「兩份都要改」陷阱。

## 整體流程

### 1. 確認要做什麼

先分辨這次任務屬於哪一種,因為後續步驟不同:

- **建立全新一週的筆記**:使用者給了新的歌詞 PDF，要產生新的一組 `詩歌敬拜歌曲/YYYY-MM-DD.html` + `詩歌主領筆記/YYYY-MM-DD.html`
- **補連結到既有筆記**:某一週的筆記已經存在，只是缺 YouTube／樂譜／歌詞PDF 連結

### 2. 收集必要輸入 —— 不要只憑一份 PDF 就動手

歌詞 PDF 通常只涵蓋「歌詞內容＋段落順序」，但每首歌完整的「連結」欄位需要三種連結，PDF 裡通常不會有：

1. **歌詞 PDF 本身的連結**（使用者提供的那個 Google Drive 分享連結）
2. **YouTube 連結**（每首歌各一個)
3. **樂譜的 Google Drive 連結**（每首歌各一個；組合曲要各自一個)

如果使用者只丟了歌詞 PDF、沒提供 YouTube 或樂譜連結，**主動問清楚**，不要留白或用猜的網址填進去——這正是這個 skill 存在的主要原因（詳見 `references/template-structure.md` 的「連結欄位」小節）。如果使用者說「之後再補」，可以先建立筆記、把連結欄位留給既有格式但註記待補，而不是編造連結。

### 3. 讀取歌詞 PDF 的內容

先確認檔案來源。如果是 Google Drive 連結：

```
mcp__Google_Drive__get_file_metadata  # 確認檔案存在、拿到 mimeType/標題
mcp__Google_Drive__read_file_content  # 先試純文字讀取（對有文字層的 PDF 有效，但通常回傳空字串）
```

如果 `read_file_content` 回傳空字串，代表這是**掃描圖片、沒有文字層**的 PDF（這是最常見的情況），改用：

```
mcp__Google_Drive__download_file_content
```

這個工具會回傳 base64。如果內容很大，結果會被存成一個本地 JSON 檔（訊息裡會給路徑），這種情況直接把那個 JSON 路徑丟給下面的腳本，不用自己手動 base64 解碼。

```bash
python3 .claude/skills/worship-notes/scripts/render_pdf_pages.py <PDF路徑或JSON路徑> <輸出資料夾> --scale 2.5
```

這支腳本會自動處理「JSON→base64 解碼→PDF」與「PDF→逐頁 PNG」兩步，並印出每一頁圖片的路徑。腳本第一次執行會自動 `pip install pypdfium2`（不需要 tesseract 或任何 OCR 引擎，也不需要 cffi/cryptography——那些是 pypdf/pdfplumber 文字擷取路徑才會踩到的坑，這裡用不到)。

拿到每頁 PNG 之後，用 **Read 工具直接讀圖**（多模態視覺閱讀），逐頁確認：

- 歌名、順序代碼（例如 `V1-V2-C1-V3-C1-C1-C2-*尾`）
- Verse／Chorus／Bridge／尾句各段的完整歌詞（含分句用的全形空白）
- 標註的和聲／主唱安排（如果 PDF 上有顏色或文字標註，可以整理成帶領筆記的參考，但不用照抄進正式筆記除非使用者要求）

一頁一頁讀完再往下走，不要只看第一頁就開始編。

### 4. 找範本、寫入內容

```bash
ls -t 詩歌敬拜歌曲/*.html | head -1     # 精簡版最新範本
ls -t 詩歌主領筆記/*.html | head -1     # 主領版最新範本
```

把找到的檔案內容讀進來，複製整份、改檔名成新日期，只替換以下內容區塊（結構、CSS、JS 一律不動）：

- `<title>` 與 `<h1>` 的日期
- `.arc-line` 的屬靈脈絡串接
- `.info` 服事同工名單、練習時間、配置說明（跟使用者確認，不要照抄上一週的人名）
- `.spine-row` 每首歌的色塊與標籤
- 每個 `.song` 區塊：`data-name`／`data-order`／`--stage`／歌詞／帶領筆記四格／連結三個 tag
- `.callout` 的樂譜下載＋歌詞全稿 PDF 連結
- `詩歌主領筆記` 版額外的口白／見證稿／唱畢後說（如果使用者沒提供草稿，先問，不要杜撰）

細節規則、四首歌超過時的配色擴充方式、`連結` 欄位的確切 HTML 格式，全部寫在 `references/template-structure.md`，動手前先看過一次。

### 5. 更新 README.md

根目錄 `README.md` 有兩個目錄表格，各自新增一列（日期新到舊排序），連到剛建立的兩份檔案。

### 6. Git 工作流程

1. `git add` 明確列出改動的檔案（新 HTML、README.md），不要 `git add -A`
2. Commit 訊息清楚描述這次變更（新增哪一週、或補了哪些連結）
3. Push 到分支——如果外部任務有指定分支名稱就用那個；否則詢問使用者要用什麼分支，或延續目前工作分支
4. **只有使用者明確要求才開 PR**，PR body 依專案慣例包含 Summary／Test plan，並附上 Generated by Claude Code 頁尾
5. **絕對不要主動合併 PR**——即使使用者之前merge 過一次，每一次合併都要重新確認。這個 repo 沒有 GitHub Pages，使用者是靠手機主畫面捷徑或某個代理連結開啟頁面，合併後如果使用者說「還是看不到」，先懷疑是瀏覽器／CDN 快取問題，而不是以為程式碼沒改到——可以請使用者長按捷徑看實際網址，或建議重新整理/清快取。

## 常見錯誤（都是實戰踩過的坑）

- **只改了一份筆記**：`詩歌敬拜歌曲/` 和 `詩歌主領筆記/` 兩份檔案的歌曲內容必須同步，改一份忘記改另一份是最常發生的疏漏。
- **把 PDF 純文字擷取的空結果當成「沒有歌詞」**：掃描版 PDF 用 `pypdf`/`pdfplumber` 的 `extract_text()` 會拿到空字串，這是正常現象，不代表失敗，直接跳去渲染成圖片用視覺閱讀即可。
- **憑空編造連結**：使用者只給歌詞 PDF、沒給 YouTube 或樂譜連結時，主動詢問，不要用猜的或留舊資料的連結。
- **手動精簡/優化 CSS**：不要因為想讓程式碼更簡潔就精簡既有的 CSS 規則（例如合併看起來重複的 `color-mix` 規則）——這些規則背後常有 light/dark 模式或不同階段色個別調校的理由，貿然精簡容易破壞某個模式下的視覺效果。
- **新增第 5 首歌只加了一半的配色**：新增 `--s5` 時，`:root` 和 `html[data-theme="dark"]` 兩個區塊、以及 `--s5-panel`，都要同步補齊，漏掉任何一個都會在某個模式或某個浮動面板顯示異常。
